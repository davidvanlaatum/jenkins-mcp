# Jenkins Tools

## Read Tools

- `jenkins_get_capabilities`: checks configured controllers, response and progressive-log cache limits, update-check status, installed plugins, optional capability warnings, and feature availability. When `updates.updateAvailable` is `true`, agents should notify the user using `updates.notificationHint`.
- `jenkins_resolve_build_url`: resolves a Jenkins build URL to controller, job path, and build number.
- `jenkins_list_jobs`: lists jobs at root or inside a folder, with optional recursive traversal, opaque cursor pagination, and filters for name, type, status, buildable/building state, last-build reference presence, last-build timestamps, last completed build JUnit summaries, Warnings NG issue presence, and coverage data presence. Job items include Jenkins buildable status. Responses use the shared paginated shape: `items`, `nextCursor`, `hasMore`, `truncated`, and `limit`; pass `nextCursor` back as `cursor` to continue with the same request filters. Cursors include all filters in their signature and are signed with an in-memory key, so changing filters or restarting the server invalidates previously issued cursors. Name filters support case-insensitive `nameContains` matching and `nameRegex` matching against both `name` and `fullName`. Type filters accept friendly names such as `folder`, `pipeline`, `multibranch`, and `freestyle`, or raw Jenkins class names. Status filters use the derived `status` field, which treats Jenkins `disabled` and not-built `color` state first, then falls back to `lastCompletedBuild.result`, non-building `lastBuild.result`, and other Jenkins `color` values; `buildable` uses Jenkins job metadata, and `building` is derived from `lastBuild.building`. Build-reference filters are `hasLastBuild`, `hasLastCompletedBuild`, `hasLastSuccessfulBuild`, and `hasLastFailedBuild`. Timestamp filters are `lastBuildAfter` / `lastBuildBefore`, `lastCompletedBuildAfter` / `lastCompletedBuildBefore`, `lastSuccessfulBuildAfter` / `lastSuccessfulBuildBefore`, and `lastFailedBuildAfter` / `lastFailedBuildBefore`; values may be RFC3339 timestamps or Unix epoch milliseconds, bounds are inclusive, and jobs missing the referenced build do not match that timestamp filter. These metadata filters are evaluated from the job-list tree query without probing JUnit, coverage, Warnings NG, or other per-build endpoints. JUnit filters are `hasTests`, `hasFailedTests`, and `hasSkippedTests`; they are evaluated only when provided, use `lastCompletedBuild`, and fetch only summary counts (`totalCount`, `failCount`, `skipCount`, `passCount`) rather than full test case details. `hasWarningsNgIssues` is evaluated only when requested, probes only each remaining job's `lastCompletedBuild` Warnings NG summary endpoint, and treats a match as at least one discovered Warnings NG tool with `total` issue count greater than zero; jobs without a last completed build do not match `hasWarningsNgIssues=true`. `hasCoverage` is evaluated only when requested, probes only each remaining job's `lastCompletedBuild` through the same supported coverage endpoints and normalization used by `jenkins_get_build`, treats missing endpoints and other non-fatal endpoint errors as no coverage, and lets caller context cancellation abort promptly; jobs without a last completed build do not match `hasCoverage=true`. Because Jenkins does not expose these plugin summaries in the job listing API, each candidate job that survives cheaper filters may require its own summary probes until the requested page plus one extra match is found or the candidate set is exhausted. Sparse positive filters can therefore probe many jobs; callers should combine them with `folder`, `recursive`, `nameContains`, `nameRegex`, `type`, `status`, `buildable`, `building`, or build metadata filters when they need to bound Jenkins API traffic. Jobs without a last completed build, with no JUnit endpoint, or with a missing JUnit report do not match positive JUnit filters. Recursive traversal scans until it either finds one additional matching job beyond the requested page or completes traversal, so `truncated` is accurate across folder boundaries when Jenkins can be scanned successfully.
- `jenkins_get_job`: returns job metadata, recent build references, and parameter definitions.
- `jenkins_get_job_config`: inspects job configuration for classic and auto-discovered jobs. `mode` defaults to `summary`; use `xml` for bounded best-effort redacted `config.xml` text or `both` for both forms. XML mode redacts common sensitive and high-risk fields, including credentials, tokens, passwords, secrets, scripts, commands, and generic values, and returns an `xml_best_effort_redaction` warning because plugin-specific XML may still require careful review. When Jenkins denies `config.xml` access, such as without Job Configure or Extended Read permissions, the tool returns fallback metadata from `api/json` with `configAccessible=false` and a structured warning. The summary extracts common multibranch, organization folder, branch-source, navigator, project factory, trigger, trait, and Pipeline script-path details when present.
- `jenkins_list_builds`: lists recent builds for a job with opaque cursor pagination and summary-field filters. Responses use the shared paginated shape: `items`, `nextCursor`, `hasMore`, `truncated`, and `limit`; pass `nextCursor` back as `cursor` to continue listing the same job with the same filters. Cursors include all filters in their signature and are signed with an in-memory key, so changing filters or restarting the server invalidates previously issued cursors. Build summaries include `result` (the Jenkins build status), `description`, `displayName`, `id`, `queueId`, `estimatedDuration`, and `keepLog`. Filters are evaluated only from those build-list summary fields and do not call full build detail endpoints. `result` accepts Jenkins result values such as `SUCCESS`, `FAILURE`, `UNSTABLE`, `ABORTED`, and `NOT_BUILT`; `building` filters running state, while `completed` is a convenience inverse and conflicts with an incompatible `building` value. Timestamp filters are `startedAfter` / `startedBefore`; values may be RFC3339 timestamps or Unix epoch milliseconds, and bounds are inclusive. Numeric range filters are `durationMillisMin` / `durationMillisMax`, `estimatedDurationMillisMin` / `estimatedDurationMillisMax`, and `numberMin` / `numberMax`. Exact filters are `keepLog` and `queueId`. Text filters are case-insensitive `descriptionContains` and `displayNameContains`. Filtered pagination scans summary pages until it finds the requested page plus one extra matching build or exhausts the build list, so `hasMore` and `truncated` reflect matching builds rather than unfiltered Jenkins rows.
- `jenkins_get_build`: returns build metadata, causes, parameters, artifacts, changes, typed Warnings NG summary data from the build-level `/warnings-ng/api/json` endpoint when available, and optional typed coverage summaries. It probes common coverage endpoints (`coverage`, `coverage/result`, and `jacoco`) after loading the build, omits coverage when endpoints are missing, returns all available summaries in probe order, and records non-fatal coverage endpoint errors without failing the build lookup.
- `jenkins_get_log`: reads bounded progressive log chunks with `start` and `nextStart` offsets. Raw pages are reused from the configured process-scoped disk cache when available. For Pipeline builds, prefer `jenkins_get_pipeline_node_log` for specific stages.
- `jenkins_search_log`: searches the progressive console log across bounded server-side pages and can include context lines. `start` chooses the initial progressive byte offset. `maxScanBytes` bounds total bytes scanned in one call, defaults to 8 MiB, and is capped at 64 MiB; legacy `maxBytes` is used as the total scan budget only when `maxScanBytes` is omitted. Responses include `scannedBytes`, `nextStart`, `more`, `scanLimitReached`, and `truncated` so callers can continue from `nextStart` when a scan budget or match limit stops the search before the end of the log. Searches with different queries reuse matching raw pages from the configured process-scoped disk cache.
- `jenkins_tail_log`: reads the tail of the console log using Jenkins progressive log offsets and reuses cached raw pages when available.
- `jenkins_get_test_report`: returns JUnit summary and bounded compact case metadata. Optional filters apply only to returned case metadata and are evaluated before `limit`, so callers receive up to `limit` matching cases. Summary counts (`totalCount`, `failCount`, `skipCount`, and `passCount`) always describe the full Jenkins test report, not the filtered subset. Filters include exact case-insensitive `status` values such as `PASSED`, `FAILED`, `REGRESSION`, or `SKIPPED`; exact suite/class/case filters `suiteName`, `className`, and `caseName` for targeted follow-up lookups; suite filters `suiteNameContains` and `suiteNameRegex`; case filters `caseNameContains` and `caseNameRegex`; class filters `classNameContains` and `classNameRegex`; and inclusive duration bounds `durationMillisMin` and `durationMillisMax`. Broad requests intentionally omit bulky `errorDetails` and `errorStackTrace` fields. When exact `className` or exact `caseName` is provided, the tool tries to fetch failure details and stack traces only for the returned matching cases; exact `suiteName` can narrow those matches but does not trigger detail fetching by itself. The response field `failureDetailsIncluded` indicates whether failure details were included. If Jenkins returns compact matches but does not expose a usable detail URL for them, the tool still returns the compact matches with `failureDetailsIncluded: false` instead of failing the request with a detail `404`. If even compact metadata exceeds Jenkins response limits, retry with exact `className` and `caseName`; the tool can then fetch summary counts plus that single case directly.
- `jenkins_get_flaky_test_stats`: analyzes compact JUnit status histories across selected builds of one job to find tests that failed in multiple builds or transitioned between states. Build selection supports a recent build-summary window with `lastBuilds` (default 20, capped at 100), explicit `builds`, or an inclusive `numberMin` / `numberMax` range, plus an optional build `result` filter. For `lastBuilds`, running builds and result-filtered builds are dropped from that bounded recent window rather than causing unbounded history scans. The tool fetches compact reports with bounded parallelism via `maxParallel` (default 4, capped at 8), drops builds with no JUnit report or no test cases, and never returns inline failure details, stack traces, logs, stage logs, or changes. Each returned test includes its suite/class/case identity, failure count, pass count, skip count, transition count, compact ordered observations, current streak, classification, and `failedBuilds` references that can be passed to `jenkins_get_test_report` with exact filters for full details. Missing observations for a particular test are ignored and do not increase transition counts. Results default to `minTransitions=3` so a single break-and-recover event is not treated as recurring flakiness; callers can set `minTransitions` to `2` or `0` for broader searches. The returned-test `limit` defaults to 25 and is capped at 200; it is applied only after computing and sorting matches by transition count descending, then failure count, latest failed build, and stable test identity. The response includes build scan totals and truncation metadata.
- `jenkins_list_lockable_resources`: List Lockable Resources plugin resources with exact name, name substring, exact label, and state filters, pagination, and client-computed label availability counts.
- `jenkins_get_build_lockable_resources`: Inspect lock step requests visible in one build's exported Pipeline flow graph without listing controller resources; includes raw arguments and visibility warnings.
- `jenkins_get_pipeline_inputs`: reads pending native Pipeline Input Step prompts and parameter definitions from exported build JSON; does not require `wfapi`. Returns exact Jenkins input IDs, messages, optional approval labels and submitter restrictions, and parameter names, descriptions, types, choices, and support flags. Defaults are omitted for all parameter types. Missing builds and permission failures remain structured errors; an existing build without pending inputs returns an empty list.
- `jenkins_get_pipeline_run`: returns Pipeline stages and pending input-step actions through Jenkins `wfapi` when the endpoints are available. Pipeline runs include `waitingForInput` and `pendingInputActions` when Jenkins reports a paused input step. If the supplemental pending-input endpoint fails after stage data is available, the run is still returned with `pendingInputError`.
- `jenkins_get_pipeline_stage`: returns a Pipeline stage and its child flow nodes.
- `jenkins_get_pipeline_node_log`: returns the bounded tail of a Pipeline flow node log through Jenkins' progressive-text endpoint, avoiding the Pipeline REST API's potentially oversized JSON log response. Equivalent requests share in-flight fetches and reuse process-scoped disk-cached raw pages when the log cache is enabled. `hasMore` and `truncated` indicate that older output was omitted by `maxBytes`. Prefer this over `jenkins_get_log` for Pipeline builds.
- `jenkins_get_replay_scripts`: returns the Jenkins Pipeline Replay script set for a build. It discovers `getReplayScripts` at the controller’s `/mcp-server/mcp` endpoint using that controller’s configured Jenkins username/API token and HTTP TLS/timeout policy, and prefers the plugin’s structured script data. With the default controller `mcpPluginMode: "discover"` (also used when omitted), it uses native Replay HTML only when initialization returns HTTP 404 or discovery confirms that the tool is absent. Set controller `mcpPluginMode: "off"`, or `JENKINS_MCP_PLUGIN_MODE=off` for all controllers, to skip upstream MCP entirely and force native HTML retrieval. Authentication/authorization failures, empty permission-limited results, malformed responses, and operational errors return normalized errors without HTML fallback. The plugin requires `Item.EXTENDED_READ` (usually implied by Job/Configure); an empty script set returns `permission_denied`. Script retrieval does not establish permission to replay. Upstream sessions close after each retrieval, discovery is bounded to 100 pages, and each upstream HTTP response is capped at 8 MiB (the same full-source ceiling as native HTML retrieval). The response includes a `sourceBuild` reference and one entry for the primary script plus any loaded scripts Jenkins exposes. Each script reports a stable `id`, `kind` (`main` or `loaded`), `sizeBytes`, `truncated`, `sha256`, and content. Plugin loaded-script names use Jenkins’ native form mapping (dots replaced with underscores), matching Replay HTML field identifiers. Ambiguous mappings are rejected. Loaded scripts also include `overrideKey`, which is the key to use in `loadedScriptOverrides` when calling `jenkins_replay_build`. By default, script bodies are returned in full; set `maxBytes` to bound each returned body. Truncated responses keep full `sizeBytes` and `sha256` metadata so callers can detect that they need to refetch without `maxBytes` before submitting a full replacement.
- `jenkins_watch_build`: bootstraps or long-polls for build completion or required Pipeline input by default (`waitFor: "completion_or_input"`); `waitFor: "change"` also wakes on Pipeline stage-status and pending input changes. Returns a short server-held watch state ID plus current build and Pipeline status. The first call without `lastState` returns immediately to establish `watch.state`; callers should pass that ID back as `lastState` on the next request, and can use `waitTimeoutMs` to bound how long a single subsequent long-poll call stays open. MCP hosts may enforce a shorter per-tool-call timeout than `waitTimeoutMs`; when the host deadline cancels the call first, the tool returns a structured `unavailable` error with a context deadline or cancellation message instead of `watch.timedOut=true`. Prefer omitting `waitTimeoutMs` to use the configured default (120000 ms / 2 minutes), or request a longer window such as 300000 ms / 5 minutes when the host supports it; the configured maximum defaults to 900000 ms / 15 minutes. Shorten the window only for a known shorter host deadline or an observed host timeout, rather than assuming a 30-second limit. Longer windows still return promptly on relevant changes. Repeat calls with the returned `watch.state`. Invalid or expired `lastState` values return `invalid_request`; callers should restart from a fresh bootstrap call without `lastState`. Both watchers share a process-local LRU cache of immutable snapshots, bounded to 1024 entries and 32 MiB of serialized state (512 KiB per snapshot). IDs are random 22-character strings; unchanged snapshots reuse their ID. Snapshots expire after 30 minutes without use. Reading a snapshot or returning its unchanged ID refreshes both recency and the idle deadline. A timer removes expired snapshots even without further requests. Idle expiry, eviction, server restart, or routing to another process invalidates IDs and requires re-bootstrap; legacy signed tokens also require re-bootstrap. With the default wait mode, required input returns immediately even if already present in `lastState`, and stage changes alone do not wake the call. Timeout responses omit `build` and `pipeline`, returning only `state`, `complete`, and `timedOut`. The latest snapshot remains cached, so a timeout can return a new ID after stage changes; always pass the returned ID onward. Bootstrap, completion, required-input, and selected change responses include the snapshot. Prefer this over `jenkins_get_build` when waiting for a running build to progress; use `jenkins_get_build` for one-off snapshots.
- `jenkins_watch_queue_item`: bootstraps or long-polls a Jenkins queue item, returning an short server-held `watch.state` ID plus explicit queue status. The first call without `lastState` returns immediately; follow-up calls pass `lastState` and wait until stable queue item fields change, the item receives an executable build, is cancelled, disappears from Jenkins' queue API, or reaches `waitTimeoutMs`. MCP hosts may enforce a shorter per-tool-call timeout than `waitTimeoutMs`; when the host deadline cancels the call first, the tool returns a structured `unavailable` error with a context deadline or cancellation message instead of `watch.timedOut=true`. Prefer omitting `waitTimeoutMs` to use the configured default (120000 ms / 2 minutes), or request a longer window such as 300000 ms / 5 minutes when the host supports it; the configured maximum defaults to 900000 ms / 15 minutes. Shorten the window only for a known shorter host deadline or an observed host timeout, rather than assuming a 30-second limit. Longer windows still return promptly on relevant changes. Repeat calls with the returned `watch.state`. Jenkins `why` text changes, such as quiet-period countdowns, do not wake the long poll unless another stable field changes or the wait timeout expires. Queue timeout responses omit `item` and `build` while retaining the state ID, status, and lifecycle flags; the latest snapshot remains cached. Terminal statuses are `executable`, `cancelled`, and `disappeared`; executable responses include `watch.build` with `{ controller, job, build, url }` when Jenkins provides a build URL that matches a configured controller, so callers can immediately switch to `jenkins_watch_build`. Invalid or expired `lastState` values return `invalid_request` and require a fresh bootstrap call.
- `jenkins_list_issues`: lists Warnings NG issues for a build with opaque cursor pagination. It first discovers available tools through the build-level `/warnings-ng/api/json` endpoint. If `tool` is omitted and exactly one tool is present, it returns issues for that tool; if multiple tools are present, it returns the typed tool summaries so callers can choose one. Issue items include typed fields such as severity, category, type, message, description, file, base name, package, module, line range, column range, fingerprint, reference, origin, author, commit, and added-at metadata.
- `jenkins_get_changes`: returns SCM change sets exposed on the build.
- `jenkins_list_artifacts`: lists build artifacts without fetching content.
- `jenkins_read_artifact`: returns small UTF-8 text artifacts inline within configured size limits.
- `jenkins_list_nodes`: Inspect Jenkins computer/executor state grouped by computer, including offline reason, assigned labels, configured/busy/idle regular executor counts, one-off executors, and current executable metadata. Executable URLs matching configured controllers include a `{ controller, job, build, url }` build reference for follow-up build/log/watch tools. Accepts optional `controller`; returns `nodes`. Known architecture, disk/temp free space, response time, memory and swap measurements are optional and permission-dependent. Idle offline executors do not imply available capacity. This is computer state, not a complete node-configuration inventory: configured zero-executor nodes may have no corresponding Computer and be absent. Responses use bounded tree queries; results exceeding `limits.maxResponseBytes` return a structured `jenkins_error` rather than a partial inventory.
- `jenkins_list_queue`: lists current Jenkins queue items.
- `jenkins_get_queue_item`: inspects a queue item by id.

## Local File Tools

- `jenkins_download_artifact`: writes an artifact into the configured safe local directory. The response always includes the server-local `path`; when `artifacts.clientDownloadDir` or `JENKINS_ARTIFACT_CLIENT_DIR` is configured, it also includes a host/client-local `clientPath` with Unix or Windows path semantics. This does not change Jenkins state and does not require `mutations.enabled`; it is annotated as a non-destructive side-effect tool because it writes to local disk.
- `jenkins_update_server`: downloads the latest released `jenkins-mcp-server` binary, verifies its checksum, and installs it on macOS/Linux or stages it on Windows for manual replacement after restart. This does not change Jenkins state and does not require `mutations.enabled`, but it is disabled unless `updates.selfUpdateEnabled` is true because it writes to the local server installation.

## Jenkins-Mutating Tools

- `jenkins_poll_scm`: Request SCM polling for a job; Jenkins decides whether changes warrant a build. Requires mutations to be enabled and a configured Poll SCM trigger on an enabled job. `accepted` confirms request acceptance only, not polling completion or a queued build.
- `jenkins_proceed_pipeline_input`: approves one pending input identified by `controller`, `job`, `build`, and exact `inputId` from `jenkins_get_pipeline_inputs`. For approval-only steps, omit `parameters`. Parameterized steps require every listed parameter explicitly: use JSON booleans for boolean inputs and strings for string, text, choice, and password inputs. Choice values must match a listed choice. Defaults are not applied; missing, extra, null, and incorrectly typed values are rejected before posting. Unsupported parameter types (including file uploads and plugin-specific types) require the Jenkins UI. Uses native `proceedEmpty` or `proceed` and preserves Jenkins submitter checks and submitter identity. Requires `mutations.enabled` and emits an audit event without submitted values. Values are redacted even when MCP tool payload logging is enabled.
- `jenkins_abort_pipeline_input`: rejects one pending input using the same identifiers, without requiring parameter values. Uses native `abort`; Jenkins enforces cancellation/submitter permissions. Rejection can abort the Pipeline unless the script handles it. Requires `mutations.enabled` and emits an audit event. Both response tools return `inputId` and `accepted`; acceptance describes the input response, not build completion. A stale or missing input returns `not_found`. After an uncertain response, inspect current inputs/build state before retrying; the tools do not retry operational failures or choose another input. Continue with `jenkins_watch_build` to track the build.
- `jenkins_trigger_build`: triggers a build or parameterized build. First call `jenkins_get_job` to discover available parameter definitions (names, types, descriptions, defaults, choices, and required flags), then supply selected values via the `parameters` map.
- `jenkins_replay_build`: replays a Pipeline build, preferring the Jenkins MCP plugin’s `replayBuild` when discovered. It discovers availability before retrieving originals, then obtains the complete original script set with `getReplayScripts`, fills omitted overrides, validates loaded-script keys, and submits one scheduling request. Plugin scheduling requires access to the original scripts (`Item.EXTENDED_READ`) as well as Jenkins’ Replay permission and sandbox approval. Public loaded-script override keys use the identifiers from `jenkins_get_replay_scripts`; the plugin submission preserves Jenkins’ original script names, including dots and underscores. The result reports `backend: "mcp_plugin"`, `queueAuthoritative: true`, `queueId`, and a controller-based `queueUrl`. It omits `scheduledBuild`: use `jenkins_get_queue_item` or `jenkins_watch_queue_item` with the same controller and `queueId` to resolve the actual build, including when other builds are scheduled concurrently. The current plugin returns its queue result in a JSON text envelope; the adapter validates that envelope and extracts only the positive queue id. Upstream credentials, TLS/timeouts, response bounds, discovery limits, and session cleanup match script retrieval. With `mcpPluginMode: "off"`, a missing MCP endpoint (initial HTTP 404), or an absent `replayBuild` tool, native Replay remains available. Unchanged native replay uses Jenkins’ Replay/Rebuild endpoint; edited replay retrieves originals through the existing plugin-first script path and submits full replacements. Native results report `backend: "native"`; `scheduledBuild` is only a prediction from the job’s `nextBuildNumber`, explicitly marked `scheduledBuildPredicted: true`, and may differ under concurrent scheduling. If native Replay redirects to a queue item, the actual queue reference is also reported. Both backends preserve the mutation gate, additive mutation annotation, audit events, and source/override metadata without returning script bodies. Authentication, authorization, tool failures, malformed/empty queue results, and transport failures are errors and never trigger scheduling fallback or automatic retries. After an uncertain scheduling outcome, inspect Jenkins before retrying to avoid duplicate builds.
- `jenkins_cancel_queue_item`: cancels a queued Jenkins item. The tool is annotated as idempotent because repeating the cancellation cannot cause another queue-state transition.
- `jenkins_cancel_build`: stops a running build. The tool is annotated as idempotent because repeating the cancellation cannot cause another build-state transition.

Jenkins-mutating tools require `mutations.enabled` or `JENKINS_MUTATIONS=true`. Polling, trigger, replay, and cancel attempts emit JSONL audit events when `audit.path` is configured. Artifact downloads are local file side effects rather than Jenkins mutations, so they remain available when Jenkins mutations are disabled.

### SCM polling

Call `jenkins_poll_scm` with `job` (including folders separated by `/`) and optionally `controller`. The tool uses the native job `POST /polling` endpoint with the existing authentication and CSRF handling. Jenkins Job/Read and Job/Build permissions are required.

Freestyle and Pipeline jobs support this endpoint. Target individual branch jobs rather than multibranch parents or organization folders; this tool does not request branch indexing. Existing jobs without the endpoint return `unsupported`; missing jobs return `not_found`.

The response is `{ "accepted": true }` when Jenkins accepts the request. Jenkins does not return the polling scheduling result: disabled jobs or jobs without a configured Poll SCM trigger may accept the request and do nothing. Configure SCM and Poll SCM first; Pipeline polling uses SCMs recorded by prior builds. Acceptance does not establish that polling started or completed, changes were detected, or a build was queued. Polling can run asynchronously and Jenkins may coalesce concurrent requests. Use existing job/build inspection tools to observe subsequent builds.

## MCP Discovery and Tool Caching

MCP discovery identifies the server with a human-readable title, description, project URL, and usage instructions. The instructions direct agents to discover Jenkins capabilities first, prefer stage-specific Pipeline logs, and prefer the configured watch wait default or longer supported waits, shortening them only for known or observed host tool-call timeouts. Because registered tool definitions are fixed for the lifetime of the process and identical for every caller, the server advertises `tools.listChanged=false` and gives `tools/list` a one-hour public cache TTL. This caches tool definitions only; Jenkins data and tool-call results are not cached by MCP.

## Diagnostics Logging

Server logs go to stderr by default. Set `JENKINS_MCP_LOG_FILE` or `logging.path` to append logs to a file, which can be easier to inspect when MCP hosts hide stdio server logs.

Set `JENKINS_MCP_LOG_TOOL_CALLS=true` or `logging.toolCalls=true` to log MCP tool call start and finish events with tool name, duration, success/error state, normalized error code, and response size. Full tool arguments and responses are only logged when `JENKINS_MCP_LOG_TOOL_PAYLOADS=true` or `logging.toolPayloads=true`; this is intended for local debugging and may include sensitive Jenkins data such as job names, build parameters, console log excerpts, and artifact content.

## Capability Discovery

`jenkins_get_capabilities` treats Jenkins plugin metadata as optional. If the configured Jenkins user cannot access `pluginManager`, the controller remains available and the response includes a structured `warnings` entry with `optional: true`; the legacy `error` field remains populated for compatibility.

Disable optional plugin discovery in restricted Jenkins deployments with `JENKINS_MCP_PLUGIN_DISCOVERY=false` or:

```json
{
  "capabilities": {
    "pluginDiscoveryEnabled": false
  }
}
```

## Lockable Resources inspection

`jenkins_list_lockable_resources` reads a bounded `tree=` query from `/lockable-resources/api/json`. Inputs are optional `controller`, exact case-sensitive `name`, case-insensitive `nameContains`, exact case-sensitive `label`, `state` (`free`, `locked`, `reserved`, `unavailable`, or `ephemeral`), `includeLabelSummary` (default true), `limit` (default 100, maximum 500), and `cursor`. Filters combine with AND. Label expressions are not supported.

The response contains `resources`, optional `labels`, `limit`, `hasMore`, `truncated`, optional `nextCursor`, and `warnings`. Resources are sorted by name. All filters and the resolved controller are bound to the cursor; pagination is a fresh view of live resource state and may shift when resources change. Resource records expose name, description, original labels, normalized `labelList`, free/locked/reserved state, reservation owner and timestamp, holder `buildName`, lock cause/reason, note, ephemeral/stolen state, and exported name/value properties. Missing boolean fields remain unknown and generate a warning for missing availability state. Timestamp values are Unix epoch milliseconds. Optional fields depend on plugin version and permissions.

Label counts cover all matching resources before pagination, using `labelsAsList` with a space-separated `labels` fallback. `unavailableCount` counts explicitly non-free resources, including queued resources; unknown state contributes only to `resourceCount`. Locked and reserved counts can overlap. The plugin's UI label table and lock wait queue are not exported through this API, so full queue inspection is unavailable.

`jenkins_get_build_lockable_resources` accepts the usual `controller`, `job`, and `build` inputs. It returns a `build` reference, `source: "pipeline_wfapi"`, `lockSteps`, and `warnings`. Each step includes `nodeId`, `stageId` when available, display name, status, raw `parameterDescription`, `ambiguous`, and `resourceNames` only for simple exact-resource descriptions. Label requests, expressions, multiple resources, and complex arguments retain the raw description when exported without inferring resource names. Some wfapi versions omit label-lock arguments entirely; those steps remain ambiguous and return a warning about the missing parameter description. These records describe requests and do not establish current ownership.

Build inspection reads `FlowGraphAction.nodes` through the build JSON API using `tree=actions[_class,nodes[id,displayName]{0,1001}]`, then fetches wfapi details only for lock start nodes. It does not rely on stage listings, which omit lock blocks in current Jenkins. Inspection is capped at 1000 graph nodes and 100 lock detail requests; caps produce explicit warnings. Locks outside named stages can be inspected. `stageId` is omitted when unavailable. An empty graph produces a warning because execution metadata may not yet be available. It does not scrape the build's `locked-resources` HTML page or scan controller-wide resources. Current ownership and full lock history are unavailable through this source. Use controller listing explicitly for current availability.

Missing resource endpoints, missing exported Pipeline graphs, or missing lock-node wfapi support return structured `unsupported` errors; a missing build remains `not_found` and permission failures remain `permission_denied`. An endpoint that exports no `resources` field is unsupported, while an exported empty resource list is a valid empty result. Both tools are read-only and work independently of Jenkins mutation settings. `jenkins_get_capabilities` includes `lockableResources: true` only when plugin discovery confirms active and enabled `lockable-resources`; false without discovery is unconfirmed and callers may still probe the listing tool.

## Responding to Pipeline input

Inspect `jenkins_get_pipeline_inputs` with the build identifiers, then use the exact returned input ID (Jenkins may capitalize a configured ID). For example:

